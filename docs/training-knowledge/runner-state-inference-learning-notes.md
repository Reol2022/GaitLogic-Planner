# Runner State Inference v1 学习说明

## 从数据库到状态 API

请求进入 `GET /api/runner-state/current` 后，认证依赖先得到 `current_user`。`RunnerStateService` 只使用该用户的 ID 查询活动周期、28 天规范化训练日志和有效计划。日志查询复用 `training_load_service._query_logs`，外部活动必须先经过既有 Garmin 解析、去重、合并和 `WorkoutLog` 关联流程。

数据依次经过：

1. A 阶段构建基础 7/28 天快照和数据质量；
2. B 阶段从同一批内存数据计算独立 21 天、周桶和高强度指标；
3. 加载并校验版本化 YAML；
4. 执行纯函数式跑量、一致性和疲劳规则；
5. 合并 Evidence、Reason Code、风险标记和 limitation；
6. FastAPI 使用统一响应 Schema 返回，不落库。

## A 与 B 的职责边界

A 阶段负责权威数据获取、去重、规范化、基础窗口聚合、完成率和数据质量。B 阶段只消费这些结果和同一次查询取得的规范化行，负责派生指标与规则解释。修改基础统计公式时先改 A 并回归 A 测试；修改推断规则时改 B 配置/纯函数并回归 B 与 A。

## 为什么必须使用独立 21 天基线

若用包含最近 7 天的 28 天均值做基线，近期突然变化会同时抬高或压低比较基准，使比值被自身稀释。`previous_21d` 与 `recent_7d` 完全不重叠，比较的是近期与此前三周周均，证据更清楚，也能准确解释窗口边界。

## volume_trend 如何计算

先检查 28 天和此前 21 天的数据充分性，再计算 `distance_previous_21d_km / 3`。基线存在且大于 0 时，用最近 7 天距离除以该周均值。状态边界全部从 YAML 读取。它仅描述距离变化，所以不能写入 `load_trend`。

## training_consistency 如何选择依据

计划至少 4 次时，计划完成率比单纯训练频率更直接，因此选择 `PLAN_COMPLETION`。计划不足时选择 `ACTIVITY_REGULARITY`，使用四个固定 7 日桶的活跃数、周均次数和 CV。计划数为 0 不是失败率 0，而是完成率不可用。

## fatigue_score 如何计算

五类信号独立判断“是否有足够证据”和“是否触发”。只有至少三类有证据才解释总分。跑量变化、RPE 差值、完成率下降、连续高强度日和高强度次数按规则加分；未触发但数据有效的信号仍计入 Evidence 覆盖率。无恢复日规则不参与 v1。

## 如何添加一条新规则

1. 先由负责人更新并审核领域设计；
2. 为阈值增加配置字段和范围/顺序校验；
3. 在推断服务中优先写无数据库副作用的纯函数；
4. 增加集中 Reason Code；
5. 输出完整 Evidence，并说明可用与跳过条件；
6. 若生成风险提示，只使用受限严重程度和建议动作；
7. 添加边界、数据不足、确定性、隐私和回归测试；
8. 更新技术文档，明确它是否为非医疗产品启发式规则。

## 如何修改阈值

只修改 `config/training/runner_state_rules_v1.yaml` 中经审核的值，同时升级 `version`，并确保 `server/domain/runner_state_rules.py` 仍能校验。运行配置变化测试确认结果随配置变化，再执行 A、B 和完整测试。不要把阈值复制到 Python 分支中，也不要将真实竞赛调优参数提交到公共仓库。

## 如何增加 Reason Code

在 `server/schemas/runner_state.py` 的 `ReasonCode` 枚举增加稳定的大写蛇形代码；在明确的 UNKNOWN 或触发分支引用；添加测试检查返回枚举和对应 Evidence。不要在路由、服务和测试中各自创建不同字符串。

## 如何编写对应测试

使用完全虚构的日期、用户和训练行，固定计算结束日与时区。至少覆盖阈值的下方、等于边界、上方、缺失字段和不足数据。窗口测试要包含结束日、`结束日-6`、`结束日-7`、`结束日-27` 和窗口外日期。对高强度连续日同时测试同日双课和普通长距离。最后验证相同输入的完整 `model_dump()` 相同。

## 三个容易混淆的边界

- `load_trend` 保持 `UNKNOWN`：当前只比较跑步距离，没有融合时长、强度和主观负荷。
- `fitness_state` 保持 `UNKNOWN`：跑量、完成率和次数不能推出竞技能力。
- 长距离不等于高强度：它是关键课，但普通有氧长距离默认不进入 `HIGH_INTENSITY_TYPES`。

## 项目负责人验收清单

- YAML 版本、阈值与已审核设计完全一致；
- API 仍只读取当前登录用户且没有第二套路由；
- previous 21d 与 recent 7d 无重叠；
- 完成率分母为计划数，计划为 0 时返回 null；
- 关键课集合没有被当作高强度集合；
- 至少三类有效信号才输出具体疲劳状态；
- Evidence 覆盖率没有被描述成预测概率；
- 训练阶段没有从文本、比赛日期或跑量猜测；
- 没有数据库迁移、状态持久化、计划写入或大模型调用；
- A、B 与完整测试通过，公开仓库安全扫描无敏感信息。
