## 1. 设计背景

C2.1 已经完成跑者状态历史快照的保存、去重、查询和权限隔离。

当前系统具备：

- 实时计算当前训练状态；
- 手动保存状态快照；
- 查询历史快照列表；
- 查询快照详情；
- 保存规则版本和完整 Evidence；
- 防止相同状态重复保存。

但这些能力仍停留在后端 API 层。

C2.2 的目标，是让跑者能够直观回答：

- 我的训练状态最近发生了什么变化；
- 跑量从什么时候开始增长；
- 疲劳信号在哪一天开始增加；
- 哪些风险提示反复出现；
- 某一天为什么得到这个状态；
- 当时的数据是否完整；
- 当时使用的是哪一版规则。

## 3. 产品入口

继续使用现有页面：

```text
/runner-state

页面顶部增加两个标签：

当前状态
历史趋势

不新增独立底部导航栏目。

默认进入：

当前状态

用户切换到“历史趋势”后再加载历史数据，避免每次进入当前状态页都产生额外请求。

4. 当前状态页新增保存能力

现有“刷新”按钮继续调用：

GET /api/runner-state/current

它只重新计算，不写数据库。

新增按钮：

保存今日状态

调用：

POST /api/runner-state/snapshots

两个按钮必须明确区分：

操作	含义
刷新状态	根据最新数据重新计算，不保存
保存今日状态	计算当前状态并写入历史快照

保存结果文案：

创建新快照
今日训练状态已保存
状态未变化
当前状态与最近保存记录一致，无需重复保存

保存按钮要求：

防止连续重复点击；
保存过程中显示加载状态；
保存失败不影响当前状态展示；
保存成功后刷新历史趋势数据；
不允许前端提交 user_id、payload 或 trigger type。
5. 历史趋势页面结构

历史趋势页按以下顺序展示：

1. 时间范围选择
2. 历史摘要
3. 跑量趋势
4. 状态时间线
5. 风险事件
6. 数据质量变化
7. 快照记录
6. 时间范围

支持：

近28天
近12周
近6个月

默认：

近28天

时间范围由后端按 Asia/Shanghai 计算，前端不根据浏览器本地日期自行推导。

建议 API 使用：

range=28d
range=12w
range=6m

精确定义：

范围	定义
28d	截止日及前27个自然日
12w	截止日及前83个自然日
6m	截止日向前推6个日历月
7. 历史趋势 API

C2.1 的列表接口返回所有快照：

GET /api/runner-state/snapshots

但同一天可能存在多个快照，且六个月内记录数可能超过 100。

因此 C2.2 建议增加：

GET /api/runner-state/snapshots/timeline

查询参数：

range=28d|12w|6m

返回每个 data_cutoff_date 最后一条快照。

同日最后一条的选择规则：

created_at DESC
id DESC

响应建议：

{
  "range": "28d",
  "start_date": "2026-06-22",
  "end_date": "2026-07-19",
  "days_with_snapshots": 12,
  "total_snapshots": 16,
  "items": []
}

要求：

只查询当前用户；
不返回完整 snapshot payload；
不返回 user_id；
不返回 payload_hash；
不重新计算历史状态；
不修改快照；
静态 /timeline 路由必须避免被 /{snapshot_id} 捕获。
8. 历史摘要

页面顶部显示：

当前范围内保存天数；
快照总数；
最近一次快照日期；
最近一次跑量趋势；
最近一次疲劳信号；
风险标记出现天数。

示例：

近28天状态记录

已记录 12 天，共保存 16 次状态
最近状态：训练压力信号有所增加
最近更新：7月18日 21:36

不生成新的综合评分。

不展示：

本月健康分 82
9. 跑量趋势图

展示两条确定性指标：

最近7天跑量；
最近28天周均跑量。

建议纵轴：

km

横轴：

data_cutoff_date

要求：

缺失值不得补零；
缺失点应断开或显示为空；
同一天只使用最后一条快照；
悬浮提示显示具体日期和数值；
移动端支持横向查看或稀疏日期刻度；
不把 volume_trend 枚举映射成连续数值曲线。

实现前先调查项目是否已有图表库。

优先级：

复用现有图表库；
复用已有图表组件；
项目没有图表能力时，再评估轻量依赖；
不为了两条折线引入庞大的可视化体系。
10. 状态时间线

分类状态不使用折线图。

展示三条状态时间线：

跑量趋势；
训练一致性；
疲劳信号。

每个日期显示状态标签。

示例：

7月12日  跑量稳定  执行稳定  暂无明显压力信号
7月15日  跑量增长  执行稳定  压力信号有所增加
7月18日  明显增长  执行波动  多项压力信号同时出现

状态变化节点应比连续不变节点更突出。

不能将：

NORMAL = 1
ELEVATED = 2
HIGH = 3

绘制成假连续曲线。

展示历史快照中的风险标记事件：

VOLUME_SPIKE

RPE_ABOVE_BASELINE

页面只说明：

12. 数据质量变化

展示：

data completeness；
evidence coverage；
RPE覆盖率；
心率覆盖率。

要求：

不称为“判断准确率”；

14. 快照详情

点击历史记录后，使用：

GET /api/runner-state/snapshots/{snapshot_id}

建议使用抽屉或移动端全屏详情。

详情展示：

快照日期；
保存时间；
触发方式；
当时的综合摘要；
四类状态；
7天与28天指标；
风险标记；
Evidence；
skipped signals；
数据质量；
limitations；
ruleset version；
snapshot schema version。

必须明确提示：

这是当时保存的训练状态，不会根据当前训练数据重新计算。

详情前端可以复用 C1 展示组件，但数据源改为保存的 snapshot_payload。

不得调用当前状态接口重新生成历史详情。

15. 触发方式中文映射

第一版：

MANUAL -> 手动保存
GARMIN_SYNC -> Garmin同步
DAILY -> 每日快照
PLAN_ADJUSTMENT -> 计划调整
SYSTEM -> 系统记录

C2.2 实际数据主要为：

MANUAL

其他映射用于后续兼容，不代表当前已经启用。

16. 空状态

没有历史记录时显示：

还没有训练状态记录

保存一次当前状态后，这里会开始形成你的训练状态时间线。

提供按钮：

返回当前状态

不自动创建快照。

17. 加载与错误处理

需要分别处理：

趋势数据加载；
快照列表加载；
快照详情加载；
保存快照；
切换时间范围。

要求：

趋势加载失败不清空已有趋势；
列表加载失败不影响当前状态；
详情加载失败关闭 loading 并显示错误；
保存失败不清空当前状态；
重复保存不是错误；
切换时间范围时防止旧请求覆盖新结果；
不在前端日志打印完整 snapshot payload。

25. 设计结论

C2.2 不负责创造新的训练判断。

它负责把已经保存的状态按照时间组织起来，让跑者看清：

状态在什么时候变化，当时发生了什么，系统为什么这样判断。

趋势展示必须忠于历史数据，不把分类标签伪装成精密曲线，也不把缺失记录补成漂亮但虚假的连续轨迹。
