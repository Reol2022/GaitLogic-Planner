## A-01 — High / P0：认证信任域隔离不完整

- 组件/定位：`server/services/auth_service.py:198`、`server/api/deps.py:25`。
- 状态：**已验证**，本地合成令牌、真实 HTTP 依赖与隔离 MySQL。
- 证据：用途受限令牌与 Web 鉴权预期不一致；内部复现另存，不在公开报告列出请求。
- 前提/影响：攻击者需先取得有效签名令牌；影响授权范围与撤销语义。不证明可伪造任意身份或跨账号签名。
- 最小方案：严格区分 Web/MCP 用途、issuer/audience；拒绝不属于 Web 的令牌；设计旧 Web token 兼容期并增加双向拒绝矩阵。
- 兼容/性能：旧 token 可能需重新登录；纯 claim 校验开销小，撤销状态检查须单独计量。
- 验收：MCP/Web 双向隔离、撤销/账号停用、scope 不提升、管理员身份仍来自数据库全部通过。

## A-02 — High / P0：通用异常日志可能包含私有 SQL 参数

- 定位：`server/common/exceptions.py:92`、`:109`；`planner_core/database/session.py:10`。
- 状态：**已验证**，隔离构造 SQLAlchemy 异常，合成敏感标记进入日志。
- 前提/影响：触发带业务绑定值的异常且日志被保留/读取；可能扩大训练、聊天等私有数据的保存与访问范围。没有读取真实生产日志。
- 方案：engine hide_parameters，加安全异常摘要；约束 SQL/Provider 日志、Trace 与保留期限，不仅脱敏前端响应。
- 兼容/性能：减少排错细节，保留安全错误类别/Trace ID；通常减少日志体积。
- 验收：参数、聊天、健康指标和凭据 canary 不进入异常日志；仍可关联故障。

## A-03 — Medium / P0：Web 退出不等于服务端撤销

- 定位：`server/api/routes/auth.py:59`、`server/services/auth_service.py:198`；默认有效期见 `planner_core/config.py`。
- 状态：**已验证**，退出后同一合成 Web token 仍有效；默认有效期 7 天。
- 前提/影响：已泄露 token 在有效期内可继续使用；数据库账号停用检查仍有效。不能表述为 MCP 撤销失败。
- 方案：明确会话策略，优先复用 MySQL session/token version，或短 access token 配套可撤销刷新；不必引入 Redis。
- 兼容/性能：需要迁移/登录兼容及额外状态查询评估。
- 验收：退出、改密、账号停用的失效策略有明确测试，前端不能只删除浏览器存储就声称全端撤销。

## A-04 — Medium / P0：公开认证入口缺少应用级滥用门控证据

- 定位：`server/api/routes/auth.py:16`、`:26`，`server/api/routes/mcp_oauth.py` 的注册/授权入口。
- 状态：应用代码未见统一频率/失败次数门控；**生产利用条件待验证**，未做密码喷洒。
- 前提/影响：若边缘也无限流，可能造成凭据猜测、账号枚举及 PBKDF2/数据库资源消耗。
- 方案：账户+可信来源的有界窗口、失败退避、明确 429/Retry-After；配合 Nginx，避免信任任意转发头。
- 兼容/性能：共享网络用户可能误限流；测试 NAT、多 Worker 和正常登录峰值。
- 验收：隔离失败登录有界；不存在可通过 Worker 切换轻易扩大的额度。

## A-05 — High（候选）/ P0：文件解析资源边界不完整

- 定位：`server/api/routes/excel.py:33`、`server/services/excel_import_service.py:53`、`server/api/routes/plan_imports.py:47`、`server/api/routes/workout_imports.py:44`。
- 状态：先全量读取及旧入口无同等限制为代码证据；**压缩展开/内存耗尽影响待验证**，未执行破坏性样本。
- 前提/影响：已登录上传，绕过/低于代理字节限制仍可能出现解压或行数放大。
- 方案：有界读取、ZIP 元数据预检、展开总量/比率/成员/行列/处理时限；同步 CPU 解析不得长时间占用事件循环。
- 兼容/性能：大合法模板需清晰拒绝，保持标准 Excel 导入回归。
- 验收：合成极端但安全样本快速拒绝；正常模板、MIME/后缀、路径及并发内存均有测试。

## A-06 — Medium / P1：AI 配额并发与跨进程语义待加强

- 定位：`server/services/coach_agent_usage_service.py:16`；`server/services/ai_plan_service.py:99`、`:505`。
- 状态：Coach 进程本地计数为**代码确认**；AI Plan 检查与成功记账之间缺少原子预占，**并发超额待专项复现**。
- 前提/影响：多 Worker、重启或并发生成；可能扩大付费调用次数。成功草稿额度不等于总请求成本上限。
- 方案：MySQL 原子预占/完成结算/超时释放，保留失败不扣成功额度与幂等；不要持有行锁等待模型。
- 兼容/性能：增加少量短事务；重点防重复收费、错误释放和热点锁。
- 验收：两连接并发、重启恢复、失败格式重试、同请求幂等均不突破预算。

## A-07 — Medium（候选）/ P1：依赖公告与部署锁定不足

- 定位：`pyproject.toml`、`web/package-lock.json`。
- 状态：扫描命中已记录；**除个别人工适用性检查外，实际产品可利用性待验证**。
- 前提/影响：依赖版本、运行模式与调用路径同时满足公告条件；开发工具风险不能直接算生产漏洞。
- 方案：建立 Python 可复现锁定/产物清单，逐项修复可达公告；npm 分 runtime/dev 评估；不要直接 audit fix --force。
- 兼容/性能：MCP 版本升级会影响协议和工具定义，Garmin 升级影响上游兼容，须跑 OAuth/TCP/同步回归。
- 验收：SBOM/锁文件可重建，例外有理由/到期日，受影响路径测试通过。

## P-01 — High / P1：混合并发请求停滞

- 定位：`server/mcp/http.py:125`、`:176`；`planner_core/database/session.py:10`。
- 状态：**已在隔离真实 TCP + MySQL 负载复现**；证据和样本见性能报告。
- 前提/影响：单 Uvicorn Worker、混合 REST/MCP 并发；50 用户阶段出现等待，不能外推所有生产配置的容量。
- 方案：先核验异步入口内同步 DB 获取/释放生命周期与线程池关系，将阻塞工作完整移至受控线程执行；配置连接预算和过载拒绝。不能仅扩大池子或 Worker 掩盖。
- 兼容/性能：需确保 ContextVar、身份、Session 线程归属和取消清理正确。
- 验收：相同 50 用户测试无停滞；压力撤除后自动恢复；业务错误、超时、未完成请求均计入，检查池归还。

## P-02 — Low / P2：日期查询排序与索引使用存在扩展成本

- 定位：`server/services/training_load_service.py:84`。
- 状态：**已 EXPLAIN**：本次使用 user_id 索引，COALESCE 日期条件及排序产生 temporary/filesort；不证明当前就是主要耗时。
- 前提/影响：长期单用户历史增长后可能扩大扫描/排序；空计划表的 ALL 扫描不应误报为大表全扫。
- 方案：先扩大合成历史量，再比较保持日期回退语义的分支查询/规范化日期与索引；不盲目加重复索引。
- 兼容/性能：不能丢失无 actual_date 的计划回退记录、正跑量休息日或跨日事实。
- 验收：相同结果集合、边界测试与 EXPLAIN ANALYZE 对照，有实际收益再迁移。
