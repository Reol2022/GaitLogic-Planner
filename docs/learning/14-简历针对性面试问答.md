# 简历针对性面试问答

适用简历：严飞，AI 应用开发实习。本文只保留高概率问题；每题都按“代码、设计、测试、问题、替代方案”准备。涉及 Framework Lab 与视觉论文的内容不在当前 GaitLogic 仓库中，必须在面试前补齐对应仓库或实验记录，不能临场猜文件路径。

## 面试前先校正三句话

1. 简历中的 RAG 表述要说明阶段：Corpus Foundation 已提交；Embedding/Vector/Retriever 仍在当前工作区；Agent 接入与 RAG Eval 未完成。不要说“已上线完整 RAG Agent”。
2. 简历中的 Docker、腾讯云、Nginx 只有部署文档/脚本能在当前仓库证明；Dockerfile、Compose 和云端配置不在仓库。准备服务器截图、脱敏命令记录或降低为“维护部署方案”。
3. Coach Agent 是只读能力：不自动修改训练计划，不做医疗诊断，也不直接让模型查询数据库。

## 1. 介绍一下 GaitLogic Planner，你解决了什么问题？

**建议回答：** 它服务有训练目标的跑者，把训练周期、每日计划、实际日志、Garmin 活动、恢复反馈、Runner State 和周复盘放在一个闭环里。Agent 不是替代规则，而是基于结构化训练事实做只读解释。

- **代码在哪：** `README.md`；`planner_core/database/models.py`；`server/main.py`；`server/services/`。
- **为什么这样设计：** 训练管理的核心是计划与执行的差异，而不是单次活动记录；因此用周期、计划、日志和统计服务串联闭环。
- **怎么测试：** `tests/test_training_calendar.py`、`tests/test_training_status.py`、`tests/test_workout_import.py`，以及 API/模型测试。
- **出过什么问题：** 全量测试曾出现训练日历汇总和 Fixture 状态/隔离不一致；排查时先区分统计口径、测试预期和共享 Fixture 污染。
- **替代方案：** 可以只用一张“训练记录表”，实现快但无法清晰表达计划、跳过、调整和计划外训练，因此没有采用。

## 2. 训练周期、计划和日志为什么分表？

**建议回答：** `PlannedWorkout` 是应做什么，`WorkoutLog` 是实际做什么；实际训练可能跳过、调整、计划外，不能覆盖原计划。`session_index` 允许同日多练。

- **代码在哪：** `planner_core/database/models.py` 中 `TrainingCycle`、`TrainingBlock`、`PlannedWorkout`、`WorkoutLog`；`server/services/planned_workout_service.py`、`workout_log_service.py`。
- **为什么这样设计：** 保留原计划、支持完成率和偏差统计，并让 Garmin 导入补充实际客观字段而不改写主观反馈。
- **怎么测试：** `tests/test_models.py`、`tests/test_training_calendar.py`、`tests/test_workout_import.py`。
- **出过什么问题：** `PlannedWorkoutPayload` 曾要求表单不应该提交的 `session_index`、`is_locked`、`plan_version`，通过区分 Create/Update Payload，而不是随意塞默认值修复。
- **替代方案：** 将计划与实际合并为一张表；缺点是审计差、无法表达计划外训练和历史计划版本。

## 3. Garmin 同步如何保证幂等和失败隔离？

**建议回答：** 同步任务用 `idempotency_key` 收敛重复建 Job，用 `sync_run_id` 表示逻辑同步运行；外部活动再由 provider + 外部活动 ID、payload hash 去重。同步事实先在 Session A 提交，自动快照在独立 Session B 后置处理，B 失败不回滚 A。

- **代码在哪：** `server/integrations/activity_sync/pipeline.py`、`outcome.py`；`server/services/garmin_sync_service.py`；`server/workers/external_sync_worker.py`；`server/services/runner_state_auto_snapshot_service.py`。
- **为什么这样设计：** 外部 Provider 会超时、重复请求和重试；训练事实比状态快照更关键，不能让可选后置能力破坏主同步。
- **怎么测试：** `tests/test_garmin_runner_state_pipeline.py`、`test_garmin_sync_material_change.py`、`test_garmin_sync_runner_state_api.py`。
- **出过什么问题：** 真实 Garmin 登录出现 DNS 解析、TLS EOF、DI token exchange 等外部失败；还处理过任务长期 queued/running、重复 lap index 和活动匹配不确定的问题。
- **替代方案：** 在路由或 Worker 各自调用快照；会产生双重触发，因此统一到 `ActivitySyncPipeline.run_job`。

## 4. Runner State 是怎么计算和保存的？

**建议回答：** 当前状态按需计算最近 7/28 天训练指标、完成率、RPE/心率覆盖、强度分类和数据质量；推断规则输出趋势、一致性、疲劳、风险与 Evidence。用户手动保存或 Garmin 有效变化后才写历史快照。

- **代码在哪：** `server/services/runner_state_service.py`、`runner_state_inference_service.py`、`runner_state_snapshot_service.py`、`runner_state_snapshot_serializer.py`。
- **为什么这样设计：** 当前查询不需要产生写入；快照需要保存当时规则版本、Evidence 和完整 payload，以支持历史解释。
- **怎么测试：** `tests/test_runner_state_service.py`、`test_runner_state_inference_service.py`、`test_runner_state_snapshots.py`、`test_runner_state_snapshot_receipts.py`。
- **出过什么问题：** 快照并发和重复保存不能只靠“先查后插”；最终依赖 canonical JSON、SHA-256 与数据库唯一约束，并在冲突后 rollback/重查。
- **替代方案：** 每次 GET current 都写库；会制造无意义历史和额外写压力，因此只在明确触发时保存。

## 5. Coach Agent 为什么不是普通聊天接口？

**建议回答：** 模型不直接访问数据库；服务端从当前认证用户构建上下文，八个只读工具经 Schema、Intent 和只读权限限制。规则决定 TODAY 的权威训练结论，模型只负责解释；Provider 失败有确定性 Fallback。

- **代码在哪：** `server/services/coach_agent_query_service.py`、`server/agent/orchestrator.py`、`registry.py`、`tools/`、`validator.py`、`fallback.py`、`server/api/routes/coach.py`。
- **为什么这样设计：** 限制模型权限，避免用户越权、工具参数失控、自动改课表和无依据结论。
- **怎么测试：** `tests/test_agent_tool_registry.py`、`test_agent_provider_gateway.py`、`test_agent_validator.py`、`test_coach_agent_api.py`、`test_agent_deterministic_fallback.py`。
- **出过什么问题：** Provider 输出虽为 JSON，仍可能语义不安全；因此在 Pydantic 后增加 Deterministic Validator，并限制最大模型/工具调用次数。
- **替代方案：** 一个 Prompt 直接拼用户数据后请求模型；实现快，但无法细化权限、测试和降级，也更容易泄露数据。

## 6. 为什么 TODAY 要把确定性事实与模型输出分离？

**建议回答：** TODAY 的 decision、计划状态、风险、数据质量、warnings、limitations 和 Evidence 都是服务端已有的确定性结果。模型重复生成它们会造成类型错误、幻觉或覆盖规则，因此只允许模型返回 answer、summary、Evidence ID。

- **代码在哪：** `server/agent/today_recommendation.py`、`server/agent/providers/openai_compatible.py`、`server/agent/prompts.py`、`server/agent/validator.py`。
- **为什么这样设计：** 让模型擅长自然语言，让系统保留训练事实和安全边界的权威性。
- **怎么测试：** `tests/test_agent_evidence_references.py`、`test_agent_provider_gateway.py`、`test_agent_today_recommendation_validator.py`。
- **出过什么问题：** DeepSeek Smoke 中模型把 `data_quality` 返回为不符合 Schema 的类型，TODAY 降级；随后拆分内部 Provider Schema 与最终公共响应。
- **替代方案：** 放宽类型为 `str | dict`、自动修补 JSON 或只改 Prompt；这些会掩盖契约错误，因此未采用。

## 7. 你简历里的 RAG 到底完成到什么程度？

**建议回答：** 已提交的 A 阶段完成知识来源、版权/版本元数据、确定性切分、Manifest 和 root hash。B 阶段的受控 Embedding、Exact Cosine Vector Store、索引和 Retriever 在当前工作区开发中，尚未提交；Agent Tool、RAG Evaluation、前端引用未完成。

- **代码在哪：** A：`knowledge/`、`server/knowledge_retrieval/{loader,chunker,manifest,corpus_service}.py`、`scripts/knowledge_corpus.py`；B：`embeddings/`、`vector_stores/`、`index_service.py`、`retriever.py`、`scripts/knowledge_index.py`。
- **为什么这样设计：** 先解决来源、版权、版本和稳定切分，再解决索引和接入；避免把未审计知识直接给 Agent。
- **怎么测试：** A：`tests/test_knowledge_corpus_*.py`；B：`tests/test_knowledge_embeddings.py`、`test_knowledge_index.py`、`test_knowledge_vector_store.py`、`test_training_knowledge_retriever.py`，但 B 仍需提交前重跑并留档。
- **出过什么问题：** 当前最大问题不是检索算法，而是阶段边界：简历容易把未提交 B、未实现 C/D/E 写成完整 RAG。索引还必须绑定 corpus root hash，避免语料变更后误用旧向量。
- **替代方案：** 直接把网页/PDF 扔进向量库；来源、版权、版本和引用不可控，因此未采用。

## 8. DeepSeek / OpenAI-compatible Provider 做了哪些安全控制？

**建议回答：** Provider 默认关闭，Key/Base URL/模型只由服务端 Settings 配置；客户端不能控制。thinking 和 response format 使用受控枚举，禁止任意 extra body；严格解析输出，不读取或回放 reasoning_content。

- **代码在哪：** `planner_core/config.py`、`server/agent/providers/security.py`、`openai_compatible.py`、`server/agent/trace.py`。
- **为什么这样设计：** 防止用户通过 URL、模型、Key 或额外 JSON 改变服务器请求边界，也让兼容逻辑可审计。
- **怎么测试：** `tests/test_agent_provider_security.py`、`tests/test_agent_provider_gateway.py`、Provider Smoke 报告。
- **出过什么问题：** DeepSeek-compatible 端点需要 `thinking: {"type":"disabled"}` 或 `json_object`；修复为显式 Settings，不做基于 HTTP 400 的隐式切换。
- **替代方案：** 向前端暴露 Provider 设置或允许 `extra_body`；灵活但安全边界过大，因此未采用。

- **代码在哪：** `docs/DEPLOYMENT.md`、`docs/REDEPLOY.md`、`scripts/deploy.ps1`。
- **为什么这样设计：** 前端静态资源由 Nginx 提供，`/api/` 反向代理到只监听本机的 FastAPI；Supervisor/Systemd 负责进程重启。
- **怎么测试：** `nginx -t`、本机 API curl、Nginx `/api/` 反代请求、后端 pytest、前端 build；真实云端测试需要保留脱敏记录。
- **出过什么问题：** 文档明确排查 `/api/api` 路径重复、502/504、8000 端口、Worker 未启动和 Provider 503。
- **替代方案：** Docker Compose/Kubernetes；当前没有对应仓库证据，不能宣称已完成。
