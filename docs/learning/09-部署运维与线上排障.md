# 09｜部署运维与线上排障

## 仓库中已存在的部署方案

`docs/DEPLOYMENT.md` 建议：浏览器 → Nginx → 前端静态文件与 `/api/` 反代 → Gunicorn + UvicornWorker → FastAPI → MySQL。`scripts/deploy.ps1` 负责本地测试、前端构建、打包、SSH 上传、远端解压、可选初始化、服务重启和 Nginx reload。

这是一套部署方案与脚本，不是已验证的 Docker/云原生生产平台。

## 关键运行配置

- 数据库：`MYSQL_HOST`、`MYSQL_PORT`、`MYSQL_USER`、`MYSQL_PASSWORD`、`MYSQL_DATABASE`。
- 认证：`JWT_SECRET_KEY`。
- CORS：`BACKEND_CORS_ORIGINS`、`BACKEND_CORS_ORIGIN_REGEX`。
- Garmin：连接器密钥、rollout、Worker 轮询等仅在服务端配置。
- Coach/Embedding Provider：默认关闭，API Key 只保留在服务端环境变量。

`.env` 不进入仓库；日志、数据库备份、Token、私有数据和派生知识索引也被 `.gitignore` 排除。

## 典型排障路径

### 502 / 504

1. `nginx -t`，确认反代配置语法。
2. 确认 Gunicorn/Uvicorn 绑定 `127.0.0.1:8000` 且端口存活。
3. 查看 Supervisor/Systemd 状态和后端错误日志。
4. 本机 `curl` 后端，再测试经 Nginx 的 `/api/`。
5. 检查 Nginx `proxy_pass` 是否错误去掉或重复 `/api` 前缀。

### 500

1. 从请求 ID、路由、时间定位安全日志，不复制敏感 body。
2. 区分 Pydantic 422、业务 400/403/404、数据库 IntegrityError、Provider 不可用 503。
3. 复现最小输入，检查事务是否 rollback。
4. 添加回归测试后再部署。

### Garmin 任务长期 queued/running

1. 确认 Worker 已启动并轮询。
2. 查询 Job 状态、错误码、`sync_run_id`、是否被其他 Worker 领取。
3. 区分 Garmin 网络/认证失败、单活动部分失败和数据库失败。
4. 不要直接修改 Job 为成功；使用已有 retry/重处理语义。

### Coach Provider 不可用

1. 确认 Provider 默认关闭还是配置缺失。
2. 不打印 Key、Base URL 或完整 Prompt。
3. 识别 `DEGRADED`：训练事实与确定性 Fallback 仍可返回，不应将其说成同步/数据库失败。
4. 对 DeepSeek-compatible 端点，确认受控 thinking/response format 配置，不允许任意 extra body。

## Docker 与云部署待办

当前没有 Dockerfile、docker-compose、Nginx 实际配置、TLS 自动续期、监控告警、集中日志或 IaC。学习/生产化顺序建议：

1. 为后端与前端定义最小 Dockerfile。
2. 用 Compose 启动 MySQL、API、Worker、Nginx。
3. 注入 `.env`，不 COPY 密钥。
4. 提供 healthcheck、迁移前备份、日志卷和回滚版本。
5. 在隔离云主机验证 HTTPS、反代、重启、备份恢复与故障演练。

完成前，简历只应写“维护部署脚本与 Nginx/Gunicorn 部署方案”。
