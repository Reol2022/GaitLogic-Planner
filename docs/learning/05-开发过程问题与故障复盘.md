# 05｜开发过程问题与故障复盘

本章只收录已从提交记录、项目文档、测试或本项目开发记录中确认的问题。没有保存完整线上日志的条目会明确写为“开发/隔离环境证据”，不伪装为生产事故。

## 1. FastAPI 路由树升级导致结构测试失效

- 时间/版本：v0.10.3 封版阶段。
- 现象：三个 API 结构测试直接遍历 `app.routes`，在 FastAPI 0.139 的 `_IncludedRouter` 结构下不能稳定取得 `path`、`methods`。
- 初步误区：修改生产路由注册方式以迎合测试。
- 根因：测试依赖框架内部路由对象，而不是公开 API 合约。
- 最终修复：新增 OpenAPI 测试辅助，使用 `app.openapi()["paths"]` 验证公开路径和 HTTP 方法；仍保留真实 `TestClient` 的 health 请求验证。
- 验证：相关 API 结构、Runner State 快照、Weekly Review 路由测试。
- 防复发：公共接口断言优先针对 OpenAPI 契约，避免依赖私有对象树。
- 面试说法：这是一次“测试适配框架内部实现变化”的问题，不是 API 消失。修复目标是让测试验证用户真正可见的接口。

## 2. Windows 全新环境缺少 Asia/Shanghai 时区数据

- 时间/版本：v0.10.3 兼容性修复。
- 现象：Windows 环境缺少系统时区数据库时，`ZoneInfo("Asia/Shanghai")` 导入失败。
- 根因：Windows 不一定提供 IANA tz database；业务代码依赖 `ZoneInfo`，但依赖声明没有带 `tzdata`。
- 修复：在 `pyproject.toml` 添加 Windows 条件依赖 `tzdata>=2024.1; platform_system == 'Windows'`。
- 没有采用的方案：捕获异常后静默回退到 UTC。这样会改变自然日窗口、跨日训练和 Runner State 的语义。
- 验证：editable install、ZoneInfo 导入、FastAPI/ORM 导入和 OpenAPI 验证。
- 面试说法：时区不是展示格式问题，而是训练 7 天/28 天自然日窗口的业务边界。

## 3. setuptools 自动包发现导致可编辑安装边界不清晰

- 时间/版本：v0.10.3 发布兼容修复。
- 现象：仓库根目录同时包含 `server`、`planner_core`、`docs`、`knowledge`、`scripts`、`web` 等目录，自动发现可能带来错误打包或 editable install 风险。
- 根因：多目录仓库没有显式限制 Python 包发现范围。
- 修复：`pyproject.toml` 使用明确 `setuptools.packages.find`，只包含 `planner_core`、`planner_core.*`、`server`、`server.*`，排除文档、知识、脚本、测试和前端目录。
- 当前限制：wheel-only 部署仍需后续明确仓库根目录 `config/knowledge` 资源的打包策略。
- 面试说法：安装通过不等于发行包边界正确；要同时检查 editable install、wheel/sdist 内容和运行时资源路径。

## 4. TrainingRuleHit 重复索引

- 时间/版本：v0.10.3 全量 pytest 恢复阶段。
- 现象：MySQL 建表时报重复索引 `ix_training_rule_hits_evaluation_id`。
- 根因：同一 `evaluation_id` 既有列级 `index=True`，又有显式 `Index`，或 ORM 与 Schema 的定义不一致。
- 修复原则：保留查询索引，但只保留一处符合项目统一风格的定义；不通过吞错或跳过测试规避。
- 防复发：新增模型时检查列级 index 与 `__table_args__`，并在 MySQL 初始化测试中覆盖表创建。
- 面试说法：索引并非“越多越好”；重复索引既会导致迁移失败，也增加写入成本和维护复杂度。

## 5. 全量测试中 Fixture 互相污染

- 时间/版本：v0.10.3 测试恢复阶段。
- 现象：训练日历状态汇总不一致、Workout Import 重复创建用户名 `runner`、Usage Event 预期 422 实际 400。
- 排查方向：先区分产品缺陷、断言过期、Fixture 隔离不足，不能把全量失败统一改断言。
- 已采取原则：为测试使用唯一虚构用户名或正确的事务隔离；明确区分 Pydantic 请求格式错误（通常 422）与路由/业务参数错误（400）。
- 防复发：测试 Fixture 不应共享可变全局状态；错误码断言必须反映项目统一异常语义。
- 当前证据边界：完整根因与最终文件差异需在对应测试提交中复核后再补充到本章。

## 6. Garmin 真实认证与网络失败

- 现象：Garmin 登录过程出现 DI token exchange 失败、域名无法解析、SSL EOF，随后 API 返回 `AUTHENTICATION_REQUIRED`。
- 根因类别：外部 Garmin SSO、账号区域、MFA、DNS、TLS 或 Provider 策略；不是仅靠本地密码字段就能修复的内部业务错误。
- 系统策略：返回脱敏安全错误；不保存明文密码、不伪造同步成功；真实连接与 Mock Provider 分离。
- 面试说法：第三方认证要把“外部不可控失败”与“内部数据一致性失败”分开处理。前者需要安全可理解的错误与重试入口，后者需要事务/幂等保护。

## 7. DeepSeek-compatible Provider 的受控兼容

- 时间/版本：v0.11.0 发布前。
- 现象：某些 OpenAI-compatible 端点需要 `thinking: {"type":"disabled"}`，或不支持最终 JSON Schema Response Format。
- 根因：兼容协议不是完全一致；直接允许任意 `extra_body` 会扩大 SSRF、配置漂移和不可审计输入风险。
- 修复：设置层只允许 `COACH_AGENT_THINKING_MODE=unset|disabled|enabled`，默认 unset；disabled 时仅添加固定 thinking 字段。`json_object` 也作为受控枚举，不自动根据 400 切换。
- 未实现：thinking 模式工具链、`reasoning_content` 读取/回放；enabled 在网络调用前安全拒绝。
- 验证：Provider Gateway 与 Security 测试、真实 Provider Smoke 的脱敏报告。

## 8. TODAY 模型输出污染权威训练事实

- 现象：模型把 `data_quality` 返回为不符合 Provider Schema 的类型，导致 TODAY 从可用建议降级；更深层风险是模型自由生成服务端已经确定的 decision、风险或 Evidence。
- 根因：Provider 输出 Schema 与公共 API 契约混用，模型承担了不应承担的确定性字段。
- 修复：拆分内部 Provider 输出与最终 API Materializer。服务端拥有 decision、计划状态、风险、数据质量、warnings、limitations 和 canonical Evidence；模型只返回 answer、summary、`key_evidence_ids`。
- 防复发：Evidence 目录由服务端生成，模型只能选择 ID；未知、重复、带空格或伪造 ID 会被拒绝。
- 面试说法：结构化输出不是只定义一个 JSON Schema，而是要明确哪些字段是模型叙述，哪些字段必须由系统权威装配。

## 排障通用顺序

```text
确认环境与版本
→ 最小复现
→ 区分输入校验 / 业务错误 / 外部依赖 / 数据库事务
→ 读取安全日志与 trace 摘要
→ 修复根因
→ 加最小回归测试
→ 复跑专项与全量
→ 更新 changelog 和面试证据
```

不要在面试中声称“从不出错”。更可信的回答是给出一个可复现问题、错误分类、根因、修复、测试和仍然存在的边界。
