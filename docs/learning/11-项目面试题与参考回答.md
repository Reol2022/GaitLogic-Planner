# 11｜项目面试题与参考回答

## 项目介绍

### 你做的项目解决什么问题？

推荐回答：GaitLogic 面向有训练目标的跑者，把周期计划、每日训练、实际日志、设备活动、恢复反馈和复盘组织成一个闭环。它的重点不是社交，而是让计划与实际执行能被持续追踪和解释。

证据：`README.md`、`planner_core/database/models.py`、训练服务与页面。

不要回答：这是一个“接了 AI 的跑步 App”。这会掩盖项目真正的训练数据建模价值。

### 最大技术难点是什么？

推荐回答：我会选 Garmin 同步和 Coach Agent 两个例子。Garmin 难在外部认证、重试、活动去重、计划匹配和同步后状态更新不能互相回滚；Coach 难在让模型解释但不让模型决定训练事实或写入计划。

## 数据库与后端追问

### 为什么训练计划和训练日志分表？

计划表达应做什么，日志表达实际做什么。拆表后才能保留跳过、调整、计划外训练和原计划对比。`WorkoutLog.planned_workout_id` 可空支持计划外活动；同日多练由 `session_index` 表达。

### 如何保证多用户隔离？

认证依赖从 JWT 获取当前用户；服务查询以当前 user_id 限定；多数数据表带 user_id 外键和以 user_id 开头的索引。外键保证归属完整性，查询过滤防止通过猜测资源 ID 越权读取。

### 数据库唯一约束和应用层校验有什么区别？

应用层校验提供友好错误和正常流程，数据库唯一约束处理并发最终竞争。比如快照去重不能只靠“先查再插”，并发时仍要依赖唯一约束并在冲突后重新查询。

## Garmin 追问

### 为什么同步后自动快照要开第二个 Session？

同步事实属于主流程。先在 Session A 提交活动和训练日志，再用 Session B 创建快照；B 失败只能得到 `FAILED_NON_BLOCKING`，不能回滚已成功的同步或改写 Job 终态。

### `sync_run_id` 和 idempotency key 分别是什么？

idempotency key 用于收敛重复创建同步任务；sync_run_id 表示同一个逻辑同步运行，可在 retry Job 间共享回执和自动快照结果。两者解决不同层次的重复。

## Agent 追问

### 这是不是普通聊天接口？

不是。模型不直接访问数据库；服务端注入当前用户并提供八个严格 Schema 的只读工具；规则决定 TODAY 的权威字段；Validator 拦截越权或无依据输出；Provider 失败时有确定性 Fallback。

### 为什么 Pydantic 之后还要 Validator？

Pydantic 验证结构和类型，但不理解业务安全。例如 JSON 格式正确，仍可能声称已修改计划、做出医疗诊断、选择不存在的 Evidence 或用 Narrative 覆盖确定性 decision。Validator 负责这些跨字段和业务语义规则。

### 为什么 TODAY 要把事实和模型回答分开？

服务端已有确定性 decision、计划状态、数据质量、风险、warnings 和 evidence。让模型再次生成这些字段会带来类型错误、幻觉和覆盖规则风险，所以模型只生成解释及 Evidence ID。

### 你的 Agent 如何评测？

使用 32 条固定日期、虚构 Fixture 的离线案例和 Deterministic Gateway，检查 Intent、工具、参数、决策、计划状态、warnings、limitations、Fallback、越权声明。它证明受控契约，不证明开放域真实效果。

## RAG 压力追问

### 你是不是已经完成 RAG？

准确回答：我已提交语料基础，包括来源、版权边界、确定性 Chunk 与 Manifest；Embedding、向量索引和 Retriever 正在工作区开发，尚未提交；Agent Tool 接入、RAG Eval 和前端引用仍未完成。因此我不会把它写成已上线 RAG Agent。

### 为什么先不用向量数据库？

第一步优先验证知识来源、版本、索引身份、过滤和引用契约。Exact Cosine Store 透明、可重复、方便测试；当契约稳定且规模/延迟需要时再换专用存储。

## 压力问题：代码是否由 Codex 写的？

建议回答：我使用 AI 辅助开发，但项目中的每个简历表述都绑定代码、测试和设计取舍。我能从业务目标、调用链、数据模型、失败复盘和限制解释设计；例如可以说明 Session A/B、TODAY 事实分离、Agent Validator 和 RAG 阶段边界。AI 生成不替代我对代码的审查、验证和责任。

不要回答：全部是 AI 写的，或者为了显得独立而否认使用过工具。

## 练习方式

每题使用“结论 → 代码路径 → 一个失败场景 → 取舍 → 当前限制”五段式回答。答不出具体文件、约束或测试时，回到对应学习文档阅读代码。

## 10 分钟模拟面试顺序

1. 用 60 秒介绍 GaitLogic 的训练闭环和目标用户。
2. 用 90 秒说明 Garmin 同步为何要有 Job、幂等和 Session A/B。
3. 用 90 秒说明 Coach Agent 如何防止模型直接改计划或伪造训练事实。
4. 用 60 秒解释 TODAY 的事实/Narrative 分离与 Evidence ID。
5. 用 60 秒说明 32 条 Evaluation 能证明什么、不能证明什么。
6. 用 60 秒说明 RAG 当前进度，并主动说出未完成的 Tool Integration 与 Eval。
7. 用 60 秒回答一个真实故障复盘。
8. 用 60 秒说明下一步的 Docker/云部署/RAG 工程计划。

### 复盘评分标准

每题按 0—2 分自评：

- 0：只会技术名词或无法给出证据。
- 1：能说明实现，但说不清取舍、失败或限制。
- 2：能给出业务目标、代码路径、测试证据、取舍和未完成边界。

总分低于 12 分时，先回到第 03、04、05、10 章补代码阅读，而不是继续背答案。
