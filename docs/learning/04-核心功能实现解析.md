## 1. 训练计划与训练日志闭环

### 业务目标

把“应该训练什么”和“实际训练了什么”分开保存，使计划、完成情况、计划外训练、主观感受和后续统计可以同时存在。

### 用户路径

创建训练周期 → 创建训练块与每日计划 → 在今日页或日历填写日志 → Dashboard、负荷、周复盘、Runner State 读取日志。

### 调用链

```text
API Route
→ training_cycle_service / planned_workout_service / workout_log_service
→ Pydantic Schema 校验
→ 当前 user_id 过滤
→ SQLAlchemy Session commit
→ 训练统计与展示服务读取
```

### 核心文件

- `server/services/training_cycle_service.py`
- `server/services/planned_workout_service.py`
- `server/services/workout_log_service.py`
- `server/services/training_load_service.py`
- `server/api/routes/training_cycles.py`
- `server/api/routes/planned_workouts.py`
- `server/api/routes/workout_logs.py`

### 异常与取舍

- 计划训练和日志一对一，但日志允许无计划外键，以支持计划外活动。
- 距离、时长、RPE、心率缺失时保持空值；统计层负责决定能否计入指标。
- `session_index` 支持同日多练，不能通过“日期唯一”简化数据模型。

### 如何讲

> 我把课表和实际执行拆开，使用户可以保留原计划，同时记录完成、跳过、调整和计划外训练。后续统计不直接相信单一表，而是把计划和日志按业务状态聚合。

## 2. Training Readiness 与训练负荷

### 业务目标

基于近期训练、恢复打卡、疼痛与数据质量给出确定性训练准备度，而不是医疗诊断。

### 调用链

```text
DailyRecoveryCheckin + WorkoutLog + PlannedWorkout
→ training_load_service.build_training_load_summary
→ readiness_assessment_service.evaluate_and_save_readiness
→ TrainingReadinessAssessment
→ Today / Readiness API 与页面
```

### 核心实现

- `session_srpe_load()` 使用时长与 RPE 聚合 session-RPE；无有效 RPE 时返回空值而不是伪造负荷。
- `readiness_assessment_service` 读取近期日志和恢复打卡，分别生成负荷、恢复、表现、疼痛等信号。
- `_decide_status()` 在数据不足时返回 `insufficient_data`；数据质量是结论的一部分。
- `evaluate_and_save_readiness()` 明确提交评估结果，便于追溯当天判断。

### 当前限制

- 是训练决策参考，不是伤病或医学风险诊断。
- 输入不足会降低状态确定性，不能把“暂无数据”解释为“恢复良好”。

## 3. Runner State 与历史快照

### 业务目标

在不落库当前状态的前提下，按需计算近期训练状态；用户手动保存或 Garmin 有效变化后才留下不可变历史快照。

### 调用链

```text
GET /api/runner-state/current
→ RunnerStateService.get_current
→ 复用 training_load_service._query_logs
→ 7/28 天窗口、完成率、RPE/心率覆盖率、强度分类
→ RunnerStateInferenceService.infer
→ RunnerStateSnapshot（当前只读结果）

POST /api/runner-state/snapshots
→ RunnerStateSnapshotService.save_current
→ 序列化、canonical JSON、SHA-256
→ 按 user + cutoff + payload_hash 去重
→ RunnerStateSnapshotRecord
```

### 状态推断边界

已实现：跑量趋势、训练一致性、疲劳信号、训练阶段的明确字段映射、风险标记、Evidence 与 reason code。

保持未知：`fitness_state`、`load_trend`、`weaknesses` 不根据现有数据虚构能力结论。

### 关键取舍

- 7 天与 previous 21 天基线独立计算，避免用包含最近 7 天的 28 天平均做自我比较。
- 长距离是关键课，不自动等于高强度。
- `completion_rate` 在计划数为 0 时为 null，不是 0 或 1。
- 完整 payload 用于审计，摘要列用于高效列表查询。

### 测试入口

- `tests/test_runner_state_service.py`
- `tests/test_runner_state_inference_service.py`
- `tests/test_runner_state_snapshots.py`
- `tests/test_runner_state_snapshot_receipts.py`

## 4. Garmin / Data Sync

### 业务目标

把外部活动从“同步成功提示”变成可追踪训练事实：连接、同步 Job、活动规范化、匹配计划、写入/合并日志、状态快照与可解释回执。

### 调用链

```text
Data Sync / Garmin API
→ DataSyncFacade
→ garmin_sync_service.enqueue_sync_job
→ BackgroundTask 或 external_sync_worker
→ ActivitySyncPipeline.run_job
→ garmin_sync_service.run_sync_job
→ ExternalActivity / WorkoutLog / link
→ GarminSyncRunOutcome
→ 独立 Session 的 RunnerStateAutoSnapshotService
```

### 核心文件

- `server/integrations/activity_sync/facade.py`
- `server/integrations/activity_sync/pipeline.py`
- `server/services/garmin_sync_service.py`
- `server/integrations/activity_sync/outcome.py`
- `server/workers/external_sync_worker.py`

### 关键设计

- Job 使用 `idempotency_key`，逻辑同步使用 `sync_run_id`。
- Material Change 只统计会影响 Runner State 的 WorkoutLog 创建或关键字段变化。
- `ExternalActivity` 以 provider + 外部活动 ID 去重；关联表限制一个活动进入一个训练日志。
- 同日多活动无法安全归属时进入 `needs_review`，而不是自动硬匹配。
- 自动快照只能在主同步提交后由 Pipeline 唯一入口发起。

### 当前限制

真实登录受 Garmin SSO、区域、MFA、网络和限流影响；系统只能返回安全错误，不能伪造登录或同步成功。

## 5. Coach Agent（v0.11.0 已发布）

### 业务目标

在不允许模型直接查询数据库或修改计划的前提下，提供“今日建议、解释当前状态、一般训练问题”的只读解释能力。

### 调用链

```text
POST /api/coach/query
→ CoachAgentQueryService
→ AgentTrainingContextBuilder
→ AgentToolRegistry（8 个只读工具）
→ GaitLogicCoachAgent
→ OpenAI-compatible Gateway
→ Pydantic 输出解析
→ Deterministic Validator
→ CoachQueryResponse
→ 失败时 DeterministicCoachFallback
```

### 工具边界

正式工具包括当前 Runner State、状态历史、近期训练、今日计划、当前训练周期、训练规则、今日训练评估、训练数据质量。Tool Registry 只注册 `read_only` 工具；每次调用都验证 Intent、输入 Schema 和输出 Schema。

### TODAY 的权威边界

TODAY 响应中 `decision`、计划状态、风险、数据质量、warnings、limitations、canonical evidence 由服务端 materialize。模型只生成叙述性 `answer`、`summary` 与引用 ID，不能用自由文本重写确定性结论。

### 降级语义

Provider 未启用、未配置、超时或输出不安全时，系统返回 `DEGRADED`，并使用已有训练事实和规则生成可用内容；这不是“模型回答成功”，也不应该伪装成服务异常页面。

### 评测

`server/agent/evaluation/` 使用固定日期、虚构 Fixture 与 DeterministicEvaluationGateway 执行 32 条案例。报告检查 Intent、必需工具、禁止工具、决策、计划状态、Warnings、Limitations、Fallback 和越权声明，不使用第二个 LLM 当裁判。
