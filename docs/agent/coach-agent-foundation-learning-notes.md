# GaitLogic Coach Agent Foundation 学习说明

## 1. 从哪里开始阅读

建议顺序：

1. `schemas.py`：先理解数据边界。
2. `tool.py` 与 `registry.py`：理解为什么模型不能执行任意函数。
3. `gateway.py`：理解模型厂商与业务编排为什么要分离。
4. `validator.py`：理解确定性安全校验。
5. `orchestrator.py`：最后看完整运行顺序。
6. 对应五组测试：验证每个边界如何被锁定。

## 2. Agent 和普通聊天接口有什么区别

普通聊天接口通常把消息交给模型并返回文本。Agent 在模型外增加了受控上下文、工具白名单、结构化输出、确定性 Validator、调用上限和 Trace。模型只能“建议调用哪个工具”，真正的权限校验和执行由服务端完成。

Tool Calling 就是模型返回一个结构化的工具名称和参数，服务端验证后执行，再把结构化结果交回模型。它不意味着模型获得 Python、数据库或操作系统执行权限。

## 3. 为什么 AgentRequest 不能直接信任客户端 user_id

多用户系统中，数据归属必须由认证上下文决定。当前 Agent 没有公共路由；未来入口应从登录态取得内部 user ID，再调用 `for_authenticated_user`。不能把请求 JSON 中的 user ID 用作归属依据。

## 4. Context Builder 为什么不查询数据库

Runner State 和训练统计已经有成熟服务。如果 Builder 自己查询，会形成第二套权限、窗口和去重逻辑。当前 Builder 只负责把调用方提供的安全 Schema 转为 JSON，并限制大小。这让领域服务与 Agent 编排保持清晰边界。

模型直接访问数据库会绕过多用户隔离、字段最小化、查询边界和审计，也可能执行不可控 SQL。因此模型只能看到现有服务已授权、已聚合的最小数据。

## 5. 为什么第一阶段只允许只读工具

读操作失败通常可以安全降级；写操作还涉及用户确认、幂等、事务、回滚和审计。先锁定只读契约能验证上下文、权限和工具调用闭环，而不会误改正式训练计划。

## 6. 如何添加一个只读工具

1. 定义严格的 Pydantic 输入和输出模型。
2. 继承 `AgentTool`。
3. 声明稳定名称、说明、允许意图、`read_only=True`。
4. 在 `execute` 中调用已有领域服务或纯函数。
5. 只返回输出模型允许的安全字段。
6. 在启动组合层显式 `registry.register(tool)`。
7. 为注册、意图权限、非法输入、正确输出和异常写测试。

不要传入裸函数，不要把数据库 Session、ORM 对象或凭据放进结果。

## 7. 为什么需要结构化输出和确定性 Validator

结构化输出让程序能验证意图、工具、风险、warnings 和 limitations，而不是从自由文本猜测。确定性 Validator 不再调用模型，所以同一输出总得到同一结果，不会增加费用，也不会把安全决策交还给概率模型。

## 8. 为什么限制为两次模型调用

第一轮只负责直接回答或选择必要工具；第二轮只负责基于工具结果给最终回答。这覆盖最小工具增强场景，同时避免开放式循环、不可控费用和重复调用。第二轮再次请求工具会被确定性拒绝。

限制轮次能避免模型不断重复工具、费用失控和不可复现的自治循环。

## 9. 为什么当前不做多 Agent

单 Agent 已能验证核心契约。多 Agent 会引入委派权限、上下文复制、错误传播、成本归属和 Trace 关联等额外问题；在单 Agent 权限和安全边界稳定前增加它没有必要。

## 10. Mock Gateway 如何测试

给 Mock 一个或两个结构化输出即可覆盖直接回答和工具增强。也可以注入固定异常测试 MODEL_FAILED。Mock 不访问网络，记录调用次数和每轮暴露的工具名称，因此可以验证意图过滤和调用上限。

## 11. Validator 为什么不是第二个“运动科学引擎”

Validator 只判断结构和安全边界，例如是否虚构已修改计划、是否输出医学诊断、是否隐藏工具失败。它不判断跑量趋势、不计算疲劳分数，也不替代 Runner State 规则引擎。

## 12. 工具失败时发生什么

注册表把异常转换为 `AGENT_TOOL_EXECUTION_FAILED`，不暴露原始异常。编排器仍允许第二轮基于剩余信息生成受限回答，但会补上 limitation，并把运行状态标记为 `TOOL_FAILED`。模型不能声称所有工具成功。

## 13. Trace 能记录什么以及如何调试

允许记录：trace/request UUID、事件类型、时间、工具名称、状态、安全错误码、耗时。

禁止记录：用户 ID、用户问题、会话内容、Context 数据、参数、工具结果、Prompt、模型回答、Token、异常堆栈。A 阶段 Trace 只在内存中用于测试和调试。

调试时用 `trace_id` 关联一次运行，按事件顺序检查请求校验、Context、模型、工具、响应校验和结束状态；只能查看安全错误码与耗时，不能把敏感正文临时塞进 Trace。

## 14. 如何增加新的意图

1. 在 `AgentIntent` 增加枚举。
2. 明确所需 Context 数据。
3. 为相关工具增加 allowed intent。
4. 增加直接回答、工具筛选、权限和校验测试。
5. 更新设计文档。

不要用新的意图绕过训练计划写入、医学诊断或身份权限。

## 15. 如何接入真实 Gateway

后续适配器只实现 `AgentLLMGateway.generate`，把厂商响应解析为 `AgentModelOutput`。密钥、超时、重试和模型配置应留在适配器或既有配置层，不能进入领域 Schema、Trace 或响应。必须先有无网络的契约测试，再增加受控集成测试。

## 16. 如何保护用户训练数据

数据必须先通过当前用户权限查询，再由既有领域服务聚合，只向 Context 提供完成任务所需字段。不能传 ORM、完整历史训练、真实身份、Token 或原始 Garmin payload。Trace、日志和 Fixture 同样遵守这一边界。

## 17. 如何调整安全上限

使用 Settings 中对应 `AGENT_*` 变量。Pydantic 会校验范围，模型调用硬上限仍为 2。修改默认值时必须同步配置测试、编排器调用上限测试和文档，不应把阈值散落到编排逻辑。

## 18. 项目负责人验收清单

- [ ] 分支从 v0.10.3 创建，原工作区修改未被带入。
- [ ] `server/agent` 导入不连接网络或数据库。
- [ ] 无 Agent 公共路由、迁移或前端页面。
- [ ] 请求、上下文、工具、模型输出和响应均为强类型。
- [ ] 未知意图在模型调用前被拒绝。
- [ ] 工具只能显式注册且仅为只读。
- [ ] 工具参数、输出、异常和权限均有测试。
- [ ] 模型最多调用两次，同一工具最多两次。
- [ ] 非法模型输出、医学诊断和计划修改声明会被拒绝。
- [ ] Trace 与日志不含敏感数据。
- [ ] Mock 测试不访问真实 LLM、Garmin 或数据库。
- [ ] 完整 pytest、安全检查和仓库隔离检查不退化。
